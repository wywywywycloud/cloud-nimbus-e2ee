## Статус и граница проектов

E2EE MVP развёрнут вручную на https://cloud.nimbus.by:9443 27 сентября 2026 года. Это публичный прототип, а не подтверждение независимого security review или физической синхронизации passkey. См. [DEPLOYMENT.md](DEPLOYMENT.md). [cloud-nimbus-e2ee](https://github.com/wywywywycloud/cloud-nimbus-e2ee) содержит Django backend под LGPL-3.0-or-later. [cloud-cypher](https://github.com/wywywywycloud/cloud-cypher) — отдельный клиент под Apache-2.0; vendored OPAQUE сохраняет свою MIT-лицензию. Старый Telegram/plaintext MVP остаётся историей и совместимостью, а не текущим описанием нового файлового потока.

```text
Браузер: cloud-cypher
  ├── OPAQUE client: пароль → локальный export_key
  ├── WebCrypto: ключ vault → ключ файла → ciphertext
  └── эксперимент: WebAuthn passkey + локальный PRF
          │ HTTPS / localhost, Django session, CSRF
          ▼
Django
  ├── opaque_auth → отдельный Node/WASM процесс → OPAQUE server
  ├── vaults → зашифрованные метаданные, квота, owner checks
  ├── passkeys → проверка WebAuthn assertions и PRF-конверт
  ├── otp_auth → обязательный TOTP как дополнительный фактор OPAQUE-входа
  ├── SQLite локально; PostgreSQL 18 на публичном сервере
  └── private media/cypher/ → только ciphertext нового API
```

Go storage gateway подготовлен отдельно и не является активным backend Django. Реальная локальная реализация использует Django default storage. Публичной раздачи `/media/` нет.

## Клиент и модель угроз

`core/client.py` отдаёт опубликованные статические файлы клиента без изменения их байтов. В клиент не подставляются Django-шаблоны, имена пользователей или API-секреты. Установлены CSP, `nosniff`, `no-store`, запрет встраивания и отсутствие внешних исполняемых зависимостей на странице; OPAQUE WASM поставляется вместе с зафиксированной версией библиотеки.

Клиент шифрует до передачи, backend не получает пароль OPAQUE, `export_key`, PRF-результат, ключ vault, ключ файла, исходное имя, MIME или открытые байты файла. Сервер видит username/Telegram ID, идентификаторы объектов, размеры ciphertext, время и запросы доступа. Эти метаданные не объявляются скрытыми.

Изменение владельца записи или выдача себе серверной сессии не создают ключ расшифрования. Однако активный поставщик страницы может заменить исполняемый JavaScript и похитить секрет при следующей работе пользователя. Независимый `cloud-cypher/tools/verify.py` сравнивает релизные файлы, HTTP-ответы или HAR с доверенным manifest и политикой заголовков. Совпадение ограничено наблюдением: оно не доказывает безопасность исходников, одинаковую выдачу другим пользователям, будущую выдачу или отсутствие ранее исполненного вредоносного кода. Manifest нельзя брать у того же непроверенного сервера и считать независимым основанием доверия.

Это приложение не заявляет абсолютную техническую невозможность расшифрования любым администратором при произвольной подмене клиента. Для такой границы нужны независимо доверенный клиент/канал обновлений и отдельная модель доверия. Потерю локальных ключей, malware на устройстве, копии получателей и уже раскрытый plaintext серверное шифрование не исправляет.

## Ключи и формат v1

Криптография файла использует нативный WebCrypto AES-256-GCM, 96-битный случайный IV и 128-битный tag. Vault получает новый случайный 256-битный ключ и UUID v4. Каждый файл получает независимые случайные ключ и UUID v4. Имя, MIME, исходный размер, file key и IV содержатся внутри метаданных, зашифрованных ключом vault. AAD связывает тип объекта, версию, vault UUID и file UUID, поэтому подмена объекта из другого контекста приводит к отказу проверки.

Конверты имеют строгий вид `{v:1, iv:<base64url>, ct:<base64url>}`. Для корневого ключа plaintext составляет 32 байта, ciphertext — 48 байт. Сервер проверяет форму, canonical base64url, длины и границы; проверить подлинность ciphertext без ключа он не может. Это задача клиента при расшифровании. Недопустимые версии и повреждённые объекты не должны приводить к выдаче частично расшифрованного содержимого.

Один файл шифруется целиком в памяти. Предел исходного файла — 50 MiB; ciphertext добавляет 16 байт. Это не streaming/resumable E2EE и не реализация загрузки терабайтных объектов. Старый resumable plaintext API нельзя включать как fallback E2EE.

## OPAQUE и сессии

Используется зафиксированная `@serenity-kit/opaque` 1.1.0 на основе `opaque-ke`/RFC 9807, без собственной реализации протокола. Серверный setup обязателен и поступает только из `OPAQUE_SERVER_SETUP`; изменение setup ломает существующие OPAQUE-записи. Node bridge принимает ограниченный JSON через stdin, не получает секреты в аргументах командной строки, ограничивает время/вывод и не передаёт текст исключений клиенту.

`OpaqueCredential` хранит registration record и версию. `OpaqueChallenge` хранит одноразовый обмен на сервере, привязанный к серверной Django-сессии и действующий 120 секунд. `serverLoginState` не отправляется браузеру и не помещается в signed-cookie session. CSRF требуется для всех изменяющих запросов; rate limits применяются по IP и идентификатору.

Контракт и статусы перечислены в [AUTH_API.md](AUTH_API.md). Регистрация использует только username/OPAQUE, затем ограниченную onboarding-сессию: Telegram → vault и passkey либо принятие риска → TOTP. Незавершённый аккаунт не имеет доступа к файловым и legacy endpoints. Последующий OPAQUE-вход всегда требует TOTP; passkey/PRF остаётся вторым криптографическим путём. Email auth и старые forms закрыты независимо от legacy flags.

Новая OPAQUE-запись и обёртка активного vault сохраняются атомарно. Смена auth hash инвалидирует другие сессии. OPAQUE session key сервер знает и для файлов он не используется; только клиентский export key защищает vault. При компрометации setup и records возможен подбор слабого пароля.

## Passkey/PRF и восстановление

TOTP обязателен для последующих парольных входов. Отдельный recovery code не используется. Пароль через OPAQUE и passkey через PRF — два пути к клиентскому секрету. Ни email, ни Telegram ID, ни TOTP seed, известный backend, сами по себе не заменяют ключ расшифрования, скрытый от администратора.

Рабочий прототип `passkeys/` проверяет WebAuthn challenge, origin/RP ID, user presence/verification, подпись и backup flags; секретный PRF-результат остаётся в браузере и защищает дополнительный конверт того же ключа vault. Серверу нельзя доверять присланный браузером признак `prf` как доказательство криптографической проверки. После регистрации предусмотрена отдельная assertion/activation с подписанными `BE=1`, `BS=1`. Перед upload обязательны Telegram, TOTP и активный passkey-конверт с этими флагами либо сохранённое принятие риска при отсутствии активного passkey. Последующий вход с `BS=0` допускает чтение, но upload блокируется до успешной assertion с `BS=1`.

Сохранившийся passkey позволяет создать новый OPAQUE password record с атомарной переупаковкой прежнего vault. Смена пароля не удаляет самостоятельный passkey-конверт. Потерянный passkey через код в привязанном Telegram и точное подтверждение `DELETE ALL FILES` запускает удаление всех **CipherFile шифрованного хранилища**, отзыв vault/envelopes/сессий и новый пустой контур. Legacy plaintext не входит в этот reset endpoint; новых plaintext-записей нет, существующие пользовательские данные по сообщению пользователя отсутствуют. Разрушительный сброс не является восстановлением прежних файлов.

Backup-eligible означает пригодность credential к backup, а `BS=1` — подписанное утверждение аутентификатора о его backup state. Это не независимая гарантия состоявшейся межустройственной синхронизации и восстановления у конкретного провайдера; реальная синхронизация не проверена. Если потеряны пароль и все доступные passkey, Telegram позволяет лишь контроль аккаунта/разрушительный сброс согласно policy; вернуть старые файлы без другого клиентского секрета нельзя. До production нужны проверка реальных аутентификаторов и независимое security review прототипа.

## Ciphertext API, квота и жизненный цикл

`/api/cypher/session/` публично выдаёт CSRF и статус аккаунта; приватные данные возвращаются только своему авторизованному пользователю. Остальные endpoints требуют Django session + CSRF:

- `POST vault/` — один активный vault с уникальным UUID и encrypted wrapped key;
- `GET/POST files/` — список encrypted metadata либо multipart ciphertext upload;
- `GET files/<uuid>/download/` — owner-checked opaque binary;
- `DELETE files/<uuid>/` — логическое удаление и durable physical cleanup;
- `POST reset/` — отзыв текущего vault, очистка его конверта и файлов.

Старая UUID vault остаётся tombstone и не используется повторно. Сброс обычного cipher vault не является миграцией legacy: соответствующий API не обещает удалить старые plaintext-данные. Разрушительный сброс passkey дополнительно отзывает passkey credentials и auth-сессии; он также ограничен шифрованным хранилищем. UI не должен смешивать два действия.

Все завершающие операции берут lock пользователя и актуального vault. Upload записывает временный объект вне этих locks, затем перед публикацией повторяет owner/vault/quota checks. Если vault отозван во время загрузки, объект не публикуется. Одновременные операции рассчитываются на PostgreSQL; SQLite остаётся локальным упрощением.

`User.used_bytes` учитывает legacy-файлы и новые ciphertext bytes, `reserved_bytes` — активные legacy-reservations. Квота по умолчанию 50 MiB. Поэтому единственный файл при пустом хранилище может содержать максимум `50 MiB - 16` исходных байт. Метаданные БД и конверты не входят в этот счётчик; перед production нужны отдельные ограничения числа объектов и объёма метаданных.

`BlobDeletion` является durable outbox: логическое удаление коммитится до физического удаления. Ошибки storage повторяются регламентной командой, брошенные staging blobs собираются после срока. Каскадное удаление аккаунта также ставит ciphertext в очередь очистки. Начатый до отзыва download и уже скачанные клиентские копии отозвать задним числом нельзя.

## Malware, preview, sharing и legacy

Серверный ClamAV не видит plaintext новых объектов. CipherFile не имеет фиктивного статуса `clean`. Превью возможно после локальной расшифровки; новый API не отдаёт открытые inline-файлы. Encrypted sharing не реализован: legacy HMAC capability/ACL не передают ключ и не становятся E2EE сами по себе.

Старые `drive/` и `sharing/` содержат папки, plaintext metadata, resumable sessions, ClamAV и HMAC ссылки. `NIMBUS_LEGACY_WRITES_ENABLED=0` запрещает новые plaintext-загрузки; Telegram обязателен для нового onboarding, отключение бота не отключает gate. Наличие legacy моделей не означает автоматическую миграцию. Ранее сохранённый plaintext и его backup не приобретают ретроспективную секретность после включения E2EE.

## Эксплуатационные ограничения

Production требует PostgreSQL, TLS, точного passkey origin/RP ID при использовании эксперимента, Telegram bot, защищённого setup/secret manager, независимой поставки клиента, scheduler очистки, проверенной recovery-модели, backup/restore и security review. Бэкапы ciphertext не заменяют пользовательские секреты. Отзыв/очистка должны учитываться при restore, чтобы восстановленная БД не открыла старые поколения. Физическое уничтожение всех backup/replica-копий определяется retention, а не строкой `DELETE`.

## Добровольный пропуск passkey

На шаге passkey пользователь может явно принять риск невосстановимой потери файлов при потере пароля. Согласие сохраняется на сервере; Telegram и TOTP остаются обязательными. При активном passkey согласие не обходит требования BE/BS. Разрушительный reset очищает согласие. Контракт и UI описаны в [AUTH_API.md](AUTH_API.md), решение — в [DECISIONS.md](DECISIONS.md). Изменение локальное; для deployment нужна миграция `accounts.0008_user_passkey_risk_accepted_at` и обновлённый клиент.


## 2026-09-27: passkey на внешнем устройстве

Клиент запрашивает создание с `authenticatorAttachment: cross-platform` и `hints: [hybrid]`, чтобы браузер предлагал телефон/QR вместо локального аутентификатора. Активация и вход тоже получают hybrid hint; для известного credential ID перечислены только внешние transports (hybrid/USB/NFC/BLE). Явный ответ `authenticatorAttachment: platform` отклоняется до отправки регистрации/assertion серверу; автоматического повтора через локальное устройство нет. Старые браузеры могут не сообщать attachment: отсутствие этого поля само по себе не считается доказательством локального устройства.

Это выбор браузерного сценария, а не новое криптографическое доказательство физического устройства. Hints зависят от поддержки браузером; внешний аутентификатор всё ещё должен поддерживать PRF и подписанные BE=1/BS=1. Обычный device-bound USB-ключ не становится подходящим из-за внешнего подключения. PRF остаётся на клиенте; серверные проверки не ослаблены. Проверка виртуального внешнего аутентификатора не подтверждает реальный телефон, QR/Bluetooth или provider sync.

Основание: [WebAuthn Level 3, hints](https://www.w3.org/TR/webauthn-3/#enum-hints).

## 2026-09-27: публичный поддомен без порта

Публичный origin — cloud.nimbus.by:9443. Nginx слушает только :9443 (IPv4/IPv6) и напрямую проксирует на Gunicorn 127.0.0.1:8000. Передаётся канонический Host с :9443, HTTPS scheme; forwarded headers перезаписываются. Nginx не занимает :80/:443. RP остаётся nimbus.by для действующих passkey; origin/CSRF — строго https://cloud.nimbus.by:9443. См. [DEPLOYMENT.md](DEPLOYMENT.md).
