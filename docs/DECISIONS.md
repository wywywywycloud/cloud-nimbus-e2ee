# Журнал решений cloud.nimbus

Обновлено 27 сентября 2026 года. Ниже сначала приведены решения текущего E2EE-контура. Старые записи сохранены в отдельной исторической части; их Telegram/plaintext/recovery правила не переопределяют текущие решения. Публичный экземпляр развёрнут вручную; см. DEPLOY-002.

## Текущие решения

### DEPLOY-002 — Ручной запуск без CI SSH-ключей

- **Основание:** 27 сентября пользователь прямо разрешил развёртывание без отсутствующих CI credentials. Развёрнут backend `05f361793f546e580c2e9de0696761a446f226b8`, client `4722feb937ad64c288fad776696a605a3170ef39` после успешных verify/postgres jobs run `36272922363`.
- **Состояние:** `nimbus.by → 13.143.141.139`, HTTPS :9443; :80/:443 перенаправляют на :9443. Сертификат Let's Encrypt, systemd renewal timer с проверкой Nginx перед reload. PostgreSQL peer/socket, приватный local storage, один Telegram polling worker, cleanup и local backup timers. Автоматический CD не настроен.
- **Исправление запуска:** collectstatic наследует private upload permissions 0600/0700; после chown root:root WSGI не мог читать статику. В release controller статика теперь root:nimbus, файлы 0640 и каталоги 0750. App читает, но не изменяет code/static; media остаётся nimbus:nimbus 0700. Схема не откатывалась; после проверки миграций/readiness/WSGI maintenance снят.
- **Сеть бота:** IPv6 Telegram timeout подтверждён; IPv4 работает. Службы web/polling получают отдельный read-only `/etc/gai.conf` с предпочтением IPv4. Глобальная сеть и TLS verification не ослаблены.
- **Проверено:** HTTPS/redirect/CSRF/private media; 10 клиентских файлов и headers совпали с manifest; maintenance, согласованный backup, checksums, isolated restore initial DB (38 migrations, без аккаунтов/файлов), пять Telegram API checks. Полный live onboarding с настоящим Telegram/contact/passkey выполняет пользователь; эти checks его не заменяют.
- **Ограничения:** один сервер, backups локальные и содержат серверные секреты; нет off-host DR/внешних alerts/load test. Real passkey provider sync не проверен. Runbook: [DEPLOYMENT.md](DEPLOYMENT.md).


### DB-001 — Явные блокировки без nullable outer joins

- PostgreSQL 18 CI run 36272093384 обнаружил реальный отказ `FOR UPDATE cannot be applied to nullable side of outer join` в passkey login и legacy удалениях файла/папки; успешный SQLite-прогон этого не выявлял.
- Исправление сохраняет блокировки конкретных записей без nullable `select_related`: user → vault → credential для passkey; user → файл/папка для удаления. Проверки owner и revoked vault сохраняются; отсутствующий vault отвергается.
- Повторный PostgreSQL run 36272437660 больше не содержит nullable-join ошибок, но выявил независимое закрытие DB connection тестами: прямой `response.close()` вне Django streaming wrapper и повторное закрытие после потребления. Тесты теперь потребляют поток через wrapper, сохраняя проверки байтов/ownership; app connection lifecycle не меняется. Полный PostgreSQL CI должен пройти повторно; SQLite не считается его заменой.
- Run 36272744161 подтвердил отсутствие обеих прежних ошибок, затем выявил test-helper `FileNotFoundError: node`: при минимальном subprocess environment Node из setup-node не находился. Helper теперь разрешает абсолютный путь до удаления окружения.

### AUTH-003 — Обязательный Telegram → passkey → TOTP, без email

- **Решение пользователя 26 сентября 2026:** username и OPAQUE-пароль, затем Telegram, затем passkey/PRF и TOTP. Email-вход/verification/recovery удалены из доступных маршрутов. AUTH-001/002, TG-007 и email-часть RECOVERY-001 ниже сохранены как история предыдущего решения и переопределены этой записью.
- **Реализация:** ограниченная 15-минутная onboarding-сессия; только текущий шаг, без файлов/legacy endpoints. Telegram одноразовый token, TTL, первый sender/chat binding, собственный contact, unique TG ID; перепривязка запрещена. Последующий OPAQUE-вход обязательно требует TOTP. Passkey остаётся криптографическим альтернативным входом. Upload безусловно требует TG + TOTP + активный BE=1/BS=1 конверт и повторную проверку под lock.
- **Reset:** код только привязанному Telegram + DELETE ALL FILES удаляет ciphertext, wrappers, OPAQUE/passkey/TOTP и отзывает сессии; затем обязателен новый пароль, пустой vault, passkey и TOTP. Старые файлы сохраняются только при наличии клиентского секрета. См. [AUTH_API.md](AUTH_API.md).
- **Граница:** физическая синхронизация provider passkey не проверена; Telegram/TOTP не расшифровывают файлы. Локальные mocks не являются проверкой доставки настоящим ботом.

### DEPLOY-001 — Подготовленная single-host конфигурация

- **Статус:** первоначальная подготовка; актуальный ручной запуск описан в DEPLOY-002.
- **Решение:** systemd, Gunicorn 1 worker/2 threads, Nginx HTTPS nimbus.by:9443, PostgreSQL и private local ciphertext; отдельный Telegram polling service. Go gateway не подключён. Release после CI и с pinned client gitlink.
- **Отказы:** ошибка миграции оставляет maintenance; автоматический DB rollback запрещён. Старый backup восстанавливается только изолированно с актуальными tombstones/revocations; иначе публикация запрещена. [DEPLOYMENT.md](DEPLOYMENT.md).

### E2EE-001 — Отдельный клиент и ciphertext-only API

- **Статус:** реализовано локально, проходит интеграционные проверки и security review.
- **Решение:** [cloud-cypher](https://github.com/wywywywycloud/cloud-cypher) использует WebCrypto AES-256-GCM, случайный vault key и независимый file key; имя/MIME/file key находятся внутри encrypted metadata. [Django backend](https://github.com/wywywywycloud/cloud-nimbus-e2ee) хранит ciphertext и конверты.
- **Инвариант:** plaintext upload endpoints выключены по умолчанию; legacy API не является fallback E2EE.
- **Границы:** v1 шифрует файл целиком в памяти, не поддерживает streaming/resumable E2EE, encrypted sharing и папки.

### AUTH-001 — OPAQUE вместо передачи пароля Django

- **Статус:** реализовано локально с `@serenity-kit/opaque` 1.1.0; используется библиотека протокола, не собственная криптография.
- **Решение:** registration record и версия хранятся на сервере; одноразовое state ограничено 120 секундами и привязано к серверной сессии. Пароль и клиентский export key не уходят backend.
- **Вход:** email/технический username; при `LOGIN_SECOND_FACTOR_REQUIRED=1` OPAQUE proof создаёт дополнительный email/TOTP challenge, и Django session появляется после его проверки. Регистрация подтверждает email.
- **Смена пароля:** новый record и новый encrypted wrapper того же vault key обновляются атомарно. Другие Django sessions инвалидируются; файлы не перешифровываются.
- **Граница:** OPAQUE не устраняет подбор слабого пароля при компрометации server setup и records и не защищает от подмены клиентской программы.

### AUTH-002 — Email-код или TOTP как дополнительный фактор

- **Статус:** реализуется и проверяется в локальном стенде.
- **Решение после уточнения пользователя:** TOTP заменяет email-код дополнительного подтверждения парольного входа. Криптографические способы получить ключ — OPAQUE-пароль или passkey/PRF.
- **Граница:** TOTP seed известен проверяющему серверу; TOTP не используется для wrapping vault и не даёт TOTP-only расшифрование. Отдельный recovery code не выбран.

### RECOVERY-001 — Вариант восстановления через passkey/PRF

- **Статус:** рабочий прототип, нуждается в проверке реальных провайдеров и security review.
- **История уточнения:** пользователь сначала употреблял слово passkey в значении OTP-генератора, затем попросил TOTP вместо email-кода и отдельно проработать passkey. Поэтому эти механизмы разделены.
- **Сохранённый passkey:** позволяет задать новый OPAQUE-пароль и атомарно переупаковать прежний vault, не меняя файлы.
- **Потерянный passkey:** подтверждённый email и точная фраза `DELETE ALL FILES` отзывают credentials/сессии и удаляют все CipherFile шифрованного хранилища; после этого создаётся пустое. Исторический legacy plaintext этим endpoint не удаляется. Пользователь сообщил об отсутствии существующих данных, новые plaintext-записи выключены.
- **Граница:** потеря пароля и всех доступных passkey не позволяет вернуть прежние файлы одним email/TOTP. Разрушительный reset не называется восстановлением данных.

### RECOVERY-EXP001 — Условия passkey-прототипа

- **Решение:** отдельный PRF-конверт того же vault key; WebAuthn UV/origin/RP/signature checks, assertion после регистрации, подписанные `BE=1`, `BS=1` для активации и upload при `PASSKEY_REQUIRED=1`. Последующий вход с `BS=0` разрешает чтение, но временно блокирует upload.
- **Границы:** backup flags — утверждения аутентификатора, не независимое доказательство межустройственной синхронизации. Physical provider sync не протестирован. Виртуальные аутентификаторы подтверждают реализованные проверки протокола, а не внешний сервис резервирования ключей.

### TG-007 — Telegram временно выключен

- **Статус:** default `TELEGRAM_ENABLED=0`.
- **Решение:** Telegram не является источником ключа и не нужен текущему E2EE-входу. Старые TG-001/TG-002/TG-006 — исторические правила legacy MVP.

### STORAGE-001 — Поколения, квота и durable cleanup

- **Статус:** реализовано локально.
- **Решение:** vault UUID после отзыва остаётся tombstone; upload повторно проверяет текущий vault и квоту в финальной транзакции. Физическое удаление выполняется через durable outbox с retry.
- **Квота:** 50 MiB считает ciphertext bytes, включая 16-байтный tag, и ранее существовавшие legacy-файлы; metadata БД не включена.
- **Границы:** активный download и внешние офлайн-копии не отзываются; backup retention и restore tombstones требуют отдельной эксплуатационной политики.

### SECURITY-001 — Ограниченная гарантия проверки браузерной поставки

- **Статус:** verifier и отдача статического клиента реализованы; независимый security review остаётся обязательным.
- **Решение:** backend отдаёт байты клиента без шаблонных вставок; независимый manifest/HTTP/HAR verifier проверяет наблюдённые файлы и заголовки.
- **Граница:** не обещать защиты от произвольной подмены исполняемого клиента тем же администратором. Verifier не является execution gate и не исправляет уже раскрытые секреты.

### SECURITY-002 — Секреты исключены из Django error reports

- **Решение:** собственный exception filter маскирует `OPAQUE_SERVER_SETUP` и служебный путь bridge; `sensitive_variables` действует также при DEBUG. Входной JSON с неверными типами/чрезмерной вложенностью отклоняется как ошибочный запрос.
- **Причина:** стандартное правило Django для секретов не распознавало имя `OPAQUE_SERVER_SETUP`. Локальный режим не должен раскрывать setup через диагностическую страницу.
- **Граница:** filter не заменяет `DEBUG=0`, TLS и закрытые служебные logs в production; нельзя намеренно писать protocol state или секреты в сообщения исключений.

### FILE-006 — AV и sharing отделены от E2EE

- **Статус:** новый API не объявляет ciphertext антивирусно проверенным; encrypted sharing не реализован.
- **Решение:** legacy ClamAV, inline previews и HMAC sharing остаются только legacy-функциями. Новые серверные endpoints не расшифровывают файлы ради этих функций.

### LICENSE-001 — Лицензии двух проектов

- **Решение:** существующий Django backend сохраняет LGPL-3.0-or-later; отдельный cloud-cypher выпускается под Apache-2.0. Vendored OPAQUE сохраняет MIT notices.

### SEC-P001 — Первоначальное предложение заменено

- **Статус:** superseded. [Первоначальный документ](E2EE_ARCHITECTURE_PROPOSAL.md) сохранён для истории.
- **Изменения:** вместо предложенных libsodium/Telegram binding/recovery kit текущая реализация использует WebCrypto и OPAQUE; Telegram выключен, TOTP отделён от шифрования, passkey/PRF реализуется как рабочий recovery-прототип с непроверенным physical sync. Первоначальное предложение нельзя читать как спецификацию работающего кода.

## Исторические решения legacy MVP

Следующие записи описывают прежний контур. Полезные решения о private storage, ownership, Django control plane и UI остаются историческим обоснованием; условия Telegram, plaintext upload, серверного AV, старых способов входа и sharing не применяются автоматически к E2EE.

## Инфраструктура

### INF-001 — Django как control plane

- **Статус:** реализовано.
- **Решение:** Django отвечает за пользователей, права, метаданные, квоты, upload sessions и выдачу capabilities.
- **Почему:** быстрое создание безопасного MVP с транзакциями и админкой.
- **Граница:** development server не используется в production.

### INF-002 — SQLite и локальный media для MVP

- **Статус:** реализовано только локально.
- **Решение:** SQLite хранит метаданные, `media/` — blobs и части.
- **Почему:** минимальная стоимость локальной проверки.
- **Граница:** одна машина, один writable filesystem; перед production переход на PostgreSQL и object storage.

### INF-003 — Отдельный data plane для больших объектов

- **Статус:** подготовлено, не интегрировано.
- **Решение:** Go gateway с HMAC capabilities, streaming, resume, range и atomic publish.
- **Почему:** Django не должен проксировать терабайтные тела.
- **Граница:** текущий gateway filesystem backend однорепличный; multi-replica требует object store.

### INF-004 — Приватные blobs

- **Статус:** реализовано.
- **Решение:** нет публичного `/media/`; скачивание только через owner/share checks.
- **Почему:** имя URL не должно обходить авторизацию.

### INF-005 — Резервирование квоты

- **Статус:** реализовано.
- **Решение:** размер резервируется транзакционно до приёма частей.
- **Почему:** конкурентные uploads не могут совместно превысить квоту.

## Telegram и регистрация

### TG-001 — 50 MiB видны до Telegram, upload закрыт

- **Статус:** реализовано.
- **Решение:** квота доступна и отображается сразу после регистрации; отсутствие `telegram_user_id` блокирует загрузку на сервере.
- **Почему:** квота и разрешение на upload — разные сущности; пользователь видит продуктовый лимит заранее.
- **UI:** под квотой выводится «Загрузка заблокирована до привязки Telegram».

### TG-002 — Telegram подтверждает upload, но не заменяет login

- **Статус:** реализовано.
- **Решение:** вход остаётся через email code/password, Telegram — обязательная проверка перед загрузкой.
- **Почему:** не связывать доступ к аккаунту с доступностью внешнего мессенджера.

### TG-003 — Deep link и одноразовая попытка

- **Статус:** реализовано.
- **Решение:** случайный token живёт 15 минут, в БД хранится digest; новая попытка инвалидирует старую.
- **Почему:** token в URL не должен быть долгоживущим credential.

### TG-004 — Поделиться только своим Telegram contact

- **Статус:** реализовано.
- **Решение:** `request_contact`, затем равенство `contact.user_id == message.from.id`.
- **Почему:** нельзя выбрать или отправить чужой аккаунт.
- **Privacy:** телефон не сохраняется приложением, хотя Telegram показывает его внутри contact card.

### TG-005 — Polling локально, webhook в production

- **Статус:** реализовано для обоих режимов.
- **Решение:** локально short polling без публичного URL; production webhook с secret header.
- **Почему short polling:** desktop/VPN proxy обрывал long-held requests.
- **Ограничение:** локальный bot живёт только пока запущен процесс.

### TG-006 — Безопасная перепривязка

- **Статус:** реализовано.
- **Решение:** старая привязка остаётся до успешного подтверждения новой; Telegram ID уникален.
- **Почему:** не оставлять аккаунт случайно без подтверждения при незавершённой перепривязке.

## Загрузка, файлы и безопасность

### FILE-001 — Возобновляемая chunked upload

- **Статус:** реализовано.
- **Решение:** initiate/status/part/complete/abort, idempotency key, SHA-256 части.
- **Почему:** восстановление после сетевых ошибок и основа для object-store multipart.

### FILE-002 — Антивирусный статус не закрывает скачивание визуально

- **Статус:** реализовано.
- **Решение:** компактный badge рядом с MIME type; отдельная кнопка скачивания остаётся доступной, если policy разрешает.
- **Почему:** строка «Сканер недоступен» ломала таблицу и перекрывала action area.

### FILE-003 — Fail-open только в development

- **Статус:** реализовано конфигурацией.
- **Решение:** `MALWARE_SCAN_REQUIRED=0` допустим локально; production должен использовать `1`.
- **Почему:** разработка возможна без ClamAV, но публичный сервис не должен выдавать непроверенный объект.

### FILE-004 — Превью только безопасных изображений

- **Статус:** реализовано.
- **Решение:** thumbnail для разрешённых image MIME types и только когда файл downloadable.
- **Почему:** не рендерить произвольный пользовательский контент inline.

### FILE-005 — Рекурсивный размер папки

- **Статус:** реализовано.
- **Решение:** показывать сумму файлов во всём поддереве вместо прочерка.
- **Почему:** размер папки должен соответствовать пользовательскому ожиданию.

## Общий доступ

### SHARE-001 — Один объект на ссылку

- **Статус:** реализовано DB constraint.
- **Решение:** share link указывает либо на файл, либо на папку.
- **Почему:** исключить неоднозначные capabilities.

### SHARE-002 — HMAC capability без database secret

- **Статус:** реализовано.
- **Решение:** token содержит UUID и HMAC, сравнение constant-time.
- **Почему:** непредсказуемая и проверяемая ссылка без хранения открытого token.

### SHARE-003 — Revision для немедленного отзыва

- **Статус:** реализовано.
- **Решение:** increment revision инвалидирует password session grants.
- **Почему:** отзыв должен действовать сразу, а не после истечения cookie.

## UI и ранее исправленные вопросы

### UI-001 — Сетка и список

- **Статус:** реализовано.
- **Решение:** пользователь может переключать полноценные grid/list views; default хранится в профиле и синхронизируется между устройствами. Список — плотная Finder-подобная таблица с колонками «Название», «Размер», «Тип» и «Изменён». Сетка — компактные значки с подписью под ними, а не широкие карточки на весь контентный блок.

### UI-002 — Папка должна выглядеть как папка

- **Статус:** реализовано.
- **Решение:** используется полноцветная папка из GNOME Adwaita 3.38. В сетке папка является самостоятельным объектом без рамки и фона карточки; в списке та же папка показана компактно в строке. Изображения используют thumbnail, остальные файлы — компактную MIME-иконку; каждый объект следует одной визуальной модели сетки.
- **Лицензия и происхождение:** локальная подвыборка официальной темы хранится в `static/icons/adwaita/`; исходный `COPYING` и атрибуция GNOME Project сохранены рядом с файлами.

### UI-003 — Превью изображений

- **Статус:** реализовано.
- **Решение:** в grid image files показывают thumbnail, остальные типы — нейтральную компактную MIME-иконку.

### UI-004 — Выбранные файлы в upload modal

- **Статус:** реализовано.

## Незакрытые production-решения

- Выбрать PostgreSQL provider и схему backup/PITR.
- Выбрать S3-compatible storage или довести gateway adapter.
- Определить предел синхронного malware scan и очередь больших объектов.
- Выбрать hosting, домен, TLS и secret manager.
- Настроить SMTP reputation, bounce handling и monitoring.
- Выбрать scheduler/worker для cleanup, rescan и purge.
- Добавить централизованные метрики, tracing и alerting.
- Провести отдельный security review и load test.

## 2026-09-27: отказ несинхронизируемого passkey

Яндекс Браузер предложил пользователю ключ только для текущего устройства. Backend отклоняет single-device credential кодом `synced_passkey_required`, а отсутствие backup state — `passkey_backup_required`. Клиент теперь объясняет эти ответы и показывает сообщение внутри onboarding-карточки, рядом с действием, даже после прокрутки. Подсказка предлагает другой способ сохранения. Требования PRF, BE=1 и BS=1 не меняются; поддержка конкретного менеджера и физическая синхронизация должны проверяться отдельно.

## 2026-09-27: QR-код настройки TOTP

Клиент строит otpauth URI для cloud.nimbus (TOTP SHA-1, 6 цифр, 30 секунд) и рисует QR локально на canvas через vendored qrcode-generator 2.0.4/MIT. Внешних QR API нет. Секрет доступен для ручного ввода в раскрывающейся секции; bitmap и поле очищаются при завершении настройки и блокировке/выходе. QR и seed маскируются на общих тестовых скриншотах; отдельный disposable synthetic QR используется только для проверки декодирования. Backend auth policy не меняется.

## 2026-09-27: добровольный пропуск passkey

Порядок настройки: OPAQUE-пароль → Telegram → passkey/PRF **или явное принятие риска** → обязательный TOTP. Белая кнопка «Пропустить» открывает диалог о невосстановимой потере файлов при потере пароля. Красная «Я принимаю риск» расположена выше фиолетовой «Вернуться к passkey»; отмена и Escape ничего не сохраняют.

`POST /api/cypher/passkey/skip/ {"accept_risk":true}` доступен только на шаге passkey в действующей onboarding-сессии и при наличии активного vault. Сервер сохраняет `User.passkey_risk_accepted_at`; session возвращает `passkey_skipped`. Это исключение из прежнего требования обязательного passkey: без активного passkey согласие разрешает настройку TOTP и upload после завершения настройки. Telegram, TOTP, CSRF, owner/vault/quota и повторная проверка при публикации upload сохраняются. При наличии активного passkey по-прежнему нужны BE=1/BS=1; согласие не обходит BS=0. Разрушительный Telegram reset очищает согласие.

Без passkey забытый пароль нельзя заменить с сохранением файлов; Telegram/TOTP не восстанавливают ключи. Разрушительный сброс остаётся способом создать пустое хранилище. Изменение реализовано локально; его наличие на публичном сервере требует отдельного deployment с миграцией.


## 2026-09-27: passkey на внешнем устройстве

Клиент запрашивает создание с `authenticatorAttachment: cross-platform` и `hints: [hybrid]`, чтобы браузер предлагал телефон/QR вместо локального аутентификатора. Активация и вход тоже получают hybrid hint; для известного credential ID перечислены только внешние transports (hybrid/USB/NFC/BLE). Явный ответ `authenticatorAttachment: platform` отклоняется до отправки регистрации/assertion серверу; автоматического повтора через локальное устройство нет. Старые браузеры могут не сообщать attachment: отсутствие этого поля само по себе не считается доказательством локального устройства.

Это выбор браузерного сценария, а не новое криптографическое доказательство физического устройства. Hints зависят от поддержки браузером; внешний аутентификатор всё ещё должен поддерживать PRF и подписанные BE=1/BS=1. Обычный device-bound USB-ключ не становится подходящим из-за внешнего подключения. PRF остаётся на клиенте; серверные проверки не ослаблены. Проверка виртуального внешнего аутентификатора не подтверждает реальный телефон, QR/Bluetooth или provider sync.

Основание: [WebAuthn Level 3, hints](https://www.w3.org/TR/webauthn-3/#enum-hints).
