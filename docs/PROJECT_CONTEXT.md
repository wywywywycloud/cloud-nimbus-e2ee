Состояние на 27 сентября 2026 года: публичный экземпляр развёрнут вручную на https://nimbus.by:9443. Backend 05f3617 и клиент 4722feb прошли CI. Эксплуатационные проверки и ограничения — в [DEPLOYMENT.md](DEPLOYMENT.md). Репозитории: [backend cloud-nimbus-e2ee](https://github.com/wywywywycloud/cloud-nimbus-e2ee), [клиент cloud-cypher](https://github.com/wywywywycloud/cloud-cypher).

## Что действует сейчас

- Django хранит аккаунты, непрозрачные зашифрованные объекты, зашифрованные метаданные и конверты ключей. Ключи файлов и открытое содержимое создаются и используются на клиенте.
- Клиент `/vault/` поставляется из отдельного проекта `cloud-cypher`; backend отдаёт его файлы без шаблонной подстановки.
- Парольный вход использует OPAQUE, затем обязательный TOTP-код. Пароль не отправляется Django; клиентский `export_key` защищает конверт случайного ключа vault. Общий с сервером `session_key` для шифрования файлов не используется. Альтернативный криптографический вход — passkey/PRF.
- Пароль можно менять без перешифрования файлов: новая OPAQUE-запись и новый конверт того же ключа vault сохраняются одной транзакцией.
- Квота 50 MiB доступна сразу; учёт включает ciphertext новых файлов и ранее существовавшие legacy-данные. Новые plaintext uploads по умолчанию запрещены.
- После username/OPAQUE-пароля следуют Telegram, passkey/PRF или принятие риска, затем обязательный TOTP. До завершения действует ограниченная onboarding-сессия. Telegram не создаёт ключи файлов; email auth отключён.
- Сервер не сканирует ciphertext как будто это открытый файл и не выставляет ему статус «проверен антивирусом». Расшифрование выполняется на клиенте.
- Новая версия не реализует encrypted sharing, папки и серверные превью. Старые функции остаются в legacy-коде и не означают поддержку E2EE.

## Вход и восстановление: рабочий прототип

TOTP обязателен при последующих парольных входах. Два способа получить клиентский секрет — OPAQUE-пароль или passkey/PRF. TOTP seed известен backend и не является ключом расшифрования. Полный контракт: [AUTH_API.md](AUTH_API.md).

Рабочий прототип passkey/PRF содержит дополнительный конверт того же ключа vault. Сохранившийся passkey позволяет задать забытый пароль и сохранить файлы; потерянный passkey через код в привязанном Telegram и `DELETE ALL FILES` ведёт к удалению всех файлов **шифрованного** хранилища и созданию нового пустого vault. Это разрушительный сброс, а не восстановление старых файлов. Legacy plaintext-данные не входят в этот endpoint; пользователь сообщил, что существующих данных нет, а новые plaintext-записи выключены.

Обязательные проверки Telegram и TOTP блокируют upload до завершения настройки. Без принятия риска требуется активный passkey-конверт с подписанными `BE=1`, `BS=1`; активация требует те же флаги. Отдельный recovery code не используется. Флаги являются утверждением аутентификатора; прототип не прошёл независимую проверку реальной межустройственной синхронизации у провайдера. Потеря пароля и всех доступных копий passkey не даёт способа вернуть прежние файлы только по Telegram/TOTP.

## Карта кода

| Компонент | Ответственность |
| --- | --- |
| `vaults/` | Ciphertext API, квота, owner checks, поколения vault, durable cleanup |
| `opaque_auth/` | OPAQUE exchanges, одноразовые серверные challenges, Node/WASM bridge, смена пароля |
| `passkeys/` | Рабочий прототип WebAuthn/PRF, конверт vault и разрушительный Telegram reset |
| `otp_auth/` | Обязательный TOTP для OPAQUE-входа |
| `cloud-cypher/` | Отдельный клиент Apache-2.0, WebCrypto и проверка поставляемых файлов |
| `accounts/` | Telegram-подтверждение и ограниченные onboarding-сессии; legacy email auth закрыт |
| `drive/`, `sharing/` | Legacy plaintext-модель, папки и ACL sharing; новые plaintext-записи выключены |
| `core/` | Отдача неизменённого клиента, аудит, rate limits, health и maintenance |
| `services/storage-gateway/` | Отдельно подготовленный Go data plane, не подключён к Django |

## Границы безопасности

Копия БД и storage без клиентских секретов не даёт открытые файлы напрямую. Администратор всё ещё может удалять данные, подменять ответы и мешать доступу. Если он подменит исполняемый браузером клиент, тот может украсть пароль, PRF-результат или ключ: WebCrypto, OPAQUE, отдельный Git-репозиторий и CSP сами по себе эту угрозу не устраняют. Независимый verifier проверяет наблюдённые байты/заголовки; он не является автоматическим запретом исполнения вредоносного кода. При компрометации OPAQUE server setup и записей возможен подбор слабого пароля.

## Незакрытые направления

Проверить ограничения выбранного passkey/PRF-прототипа и Telegram/TOTP-подтверждения; закончить независимое security review; проверить реальные браузеры и провайдеры аутентификаторов; настроить off-host encrypted backup, полноценный restore с актуальными отзывами, мониторинг и secret manager. PostgreSQL, TLS, Telegram polling, локальные backups и ручной deployment уже работают; автоматический CD без CI SSH credentials не настроен. Не обещать абсолютную защиту от активного поставщика браузерного кода или уничтожение чужих офлайн-копий.

## Добровольный пропуск passkey

На шаге passkey пользователь может явно принять риск невосстановимой потери файлов при потере пароля. Согласие сохраняется на сервере; Telegram и TOTP остаются обязательными. При активном passkey согласие не обходит требования BE/BS. Разрушительный reset очищает согласие. Контракт и UI описаны в [AUTH_API.md](AUTH_API.md), решение — в [DECISIONS.md](DECISIONS.md). Изменение локальное; для deployment нужна миграция `accounts.0008_user_passkey_risk_accepted_at` и обновлённый клиент.
