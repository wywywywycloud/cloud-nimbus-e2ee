# Контекст проекта cloud.nimbus

Состояние на 26 сентября 2026 года: локальная интеграция клиентского шифрования и OPAQUE. Публичный production не развёрнут. Репозитории: [backend cloud-nimbus-e2ee](https://github.com/wywywywycloud/cloud-nimbus-e2ee), [клиент cloud-cypher](https://github.com/wywywywycloud/cloud-cypher).

## Что действует сейчас

- Django хранит аккаунты, непрозрачные зашифрованные объекты, зашифрованные метаданные и конверты ключей. Ключи файлов и открытое содержимое создаются и используются на клиенте.
- Клиент `/vault/` поставляется из отдельного проекта `cloud-cypher`; backend отдаёт его файлы без шаблонной подстановки.
- Парольный вход использует OPAQUE, затем дополнительный код: email либо подключённый TOTP-генератор. Пароль не отправляется Django; клиентский `export_key` защищает конверт случайного ключа vault. Общий с сервером `session_key` для шифрования файлов не используется. Альтернативный криптографический вход — passkey/PRF.
- Пароль можно менять без перешифрования файлов: новая OPAQUE-запись и новый конверт того же ключа vault сохраняются одной транзакцией.
- Квота 50 MiB доступна сразу; учёт включает ciphertext новых файлов и ранее существовавшие legacy-данные. Новые plaintext uploads по умолчанию запрещены.
- Telegram выключен по умолчанию и не участвует в создании ключей или текущем входе.
- Сервер не сканирует ciphertext как будто это открытый файл и не выставляет ему статус «проверен антивирусом». Расшифрование выполняется на клиенте.
- Новая версия не реализует encrypted sharing, папки и серверные превью. Старые функции остаются в legacy-коде и не означают поддержку E2EE.

## Вход и восстановление: рабочий прототип

Пользователь уточнил роль TOTP: генератор одноразовых кодов заменяет код из email как дополнительное подтверждение парольного входа. Два способа получить клиентский секрет — пароль через OPAQUE или passkey через WebAuthn PRF. TOTP сам по себе не расшифровывает файлы: общий seed известен backend и не является секретом от его администратора.

Рабочий прототип passkey/PRF содержит дополнительный конверт того же ключа vault. Сохранившийся passkey позволяет задать забытый пароль и сохранить файлы; потерянный passkey через подтверждённый email и `DELETE ALL FILES` ведёт к удалению всех файлов **шифрованного** хранилища и созданию нового пустого vault. Это разрушительный сброс, а не восстановление старых файлов. Legacy plaintext-данные не входят в этот endpoint; пользователь сообщил, что существующих данных нет, а новые plaintext-записи выключены.

`PASSKEY_REQUIRED=1` блокирует upload до активного passkey-конверта с подписанными `BE=1`, `BS=1`; активация требует те же флаги. Отдельный recovery code не используется. Флаги являются утверждением аутентификатора; прототип не прошёл независимую проверку реальной межустройственной синхронизации у провайдера. Потеря пароля и всех доступных копий passkey не даёт способа вернуть прежние файлы только по email/TOTP.

## Карта кода

| Компонент | Ответственность |
| --- | --- |
| `vaults/` | Ciphertext API, квота, owner checks, поколения vault, durable cleanup |
| `opaque_auth/` | OPAQUE exchanges, одноразовые серверные challenges, Node/WASM bridge, смена пароля |
| `passkeys/` | Рабочий прототип WebAuthn/PRF, конверт vault и разрушительный email reset |
| `otp_auth/` | Email-код или TOTP как дополнительное подтверждение OPAQUE-входа |
| `cloud-cypher/` | Отдельный клиент Apache-2.0, WebCrypto и проверка поставляемых файлов |
| `accounts/` | Email-подтверждение, Django sessions и lifecycle аккаунта; legacy auth/TG сохранены отдельно |
| `drive/`, `sharing/` | Legacy plaintext-модель, папки и ACL sharing; новые plaintext-записи выключены |
| `core/` | Отдача неизменённого клиента, аудит, rate limits, health и maintenance |
| `services/storage-gateway/` | Отдельно подготовленный Go data plane, не подключён к Django |

## Границы безопасности

Копия БД и storage без клиентских секретов не даёт открытые файлы напрямую. Администратор всё ещё может удалять данные, подменять ответы и мешать доступу. Если он подменит исполняемый браузером клиент, тот может украсть пароль, PRF-результат или ключ: WebCrypto, OPAQUE, отдельный Git-репозиторий и CSP сами по себе эту угрозу не устраняют. Независимый verifier проверяет наблюдённые байты/заголовки; он не является автоматическим запретом исполнения вредоносного кода. При компрометации OPAQUE server setup и записей возможен подбор слабого пароля.
