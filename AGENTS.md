# Правила работы с cloud.nimbus

Перед изменениями прочитай `docs/PROJECT_CONTEXT.md`, `docs/INFRASTRUCTURE.md`, `docs/DECISIONS.md` и `docs/OPERATIONS.md`.

## Рабочие правила

- Не меняй архитектуру, безопасность, квоту, auth/recovery, sharing или UI-модель молча: одновременно обновляй документацию и журнал решений.
- Основной файловый поток — E2EE через отдельный клиент cloud-cypher и `vaults/`. Новые plaintext-записи по умолчанию запрещены. Не добавляй plaintext fallback и серверные ключи расшифрования.
- Парольный вход — OPAQUE. Не отправляй пароль на Django и не используй серверный OPAQUE session key для шифрования файлов. Смена record и обёртки активного vault должна быть атомарной.
- Обязательный порядок регистрации: username и OPAQUE-пароль → Telegram → passkey/PRF или явное принятие риска его отсутствия → TOTP. До завершения разрешена только ограниченная onboarding-сессия; email auth/verification/recovery запрещены.
- Два криптографических пути входа — OPAQUE-пароль и passkey/PRF. TOTP обязательно дополнительно подтверждает последующие парольные входы до выдачи сессии. TOTP с seed на сервере не является ключом расшифрования. Отдельный recovery code не используется.
- Passkey/PRF — рабочий прототип: сохранённый passkey позволяет новый пароль с прежними файлами; утраченный passkey через код в привязанном Telegram + DELETE ALL FILES удаляет все файлы шифрованного хранилища и создаёт пустое. Не выдавай разрушительный reset за восстановление старых данных и не обещай удаления legacy plaintext этим endpoint.
- Upload также требует Telegram и подключённый TOTP. Активация passkey и upload при активном passkey требуют подписанных `BE=1`, `BS=1`. Без активного passkey upload разрешён только после сохранённого принятия риска и завершения TOTP. Это утверждение аутентификатора, а не независимая гарантия физической синхронизации у провайдера; реальная межустройственная синхронизация ещё не проверена.
- Не преувеличивай защиту от активного администратора, способного заменить браузерный код. Отдельный Git и verifier не являются запретом исполнения подменённой страницы.
- Не добавляй в репозитории server setup, `.env*`, Telegram token, БД, пользовательские файлы, `.venv`, собранную статику или отчёты с секретами. Серверный OPAQUE setup не менять у работающей БД без отдельного плана.
- Файлы приватны: нет публичного `media/`; owner/vault checks обязательны, включая повторную проверку перед публикацией upload. Отзыв vault должен отзывать дополнительные key envelopes.
- Ciphertext нельзя помечать «проверен антивирусом». Encrypted sharing не реализован; legacy ACL-ссылки не заменяют выдачу ключей.
- Go storage gateway подготовлен, но не подключён. Не называй его активным backend без adapter и тестов.
- Backend остаётся LGPL-3.0-or-later; отдельный cloud-cypher — Apache-2.0. Сохраняй notices зависимостей.
- Для моделей нужны миграции. Проверяй auth isolation, CSRF, replay/expiry, races reset/upload, quota, malformed envelopes и очистку. Для UI проверяй актуальные сценарии, светлую/тёмную тему и мобильную ширину; для legacy-правок также list/grid.
- Не возвращай неработающие настройки и обещания будущих функций. Публичный экземпляр развёрнут вручную на https://cloud.nimbus.by; фактический статус и ограничения — в docs/DEPLOYMENT.md.

## Базовая проверка

```bash
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py check
.venv/bin/python manage.py test
.venv/bin/python scripts/test_e2ee.py --report-dir reports
```

Старт окружения и однократная генерация секретного OPAQUE setup описаны в `docs/OPERATIONS.md`. Результаты тестового аутентификатора не выдавать за проверку физического provider sync.
